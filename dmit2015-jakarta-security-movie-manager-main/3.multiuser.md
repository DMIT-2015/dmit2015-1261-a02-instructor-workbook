# Part 2 – Multi-User Data Ownership


This lesson follows RBAC Security, beginning with Slide 41 of the Jakarta Security presentation.


## Introduction — What are we doing today?


In our previous lesson, we configured Keycloak and Jakarta Security so users could log in to Movie Manager. Currently, our application manages a shared collection of movies. Different users can see the same records. Today, we're going to change our application into a multi-user application, where each movie belongs to a particular user. When a user creates a movie, we'll save their username with that movie. When they view the movie list, we'll use their username and role to decide which movies they can see. Sales users will see their own movies, while Administration users will be able to see all movies.


## Step 1 — Add ownership information to the Movie entity


First, we need a way to identify who owns each movie. Right now, the movie has information such as its title, genre, rating, and price. We'll add a username property so that each movie can be associated with a user.

`src/main/java/dmit2015/entity/Movie.java`


We're adding a username field to the Movie entity. This allows us to associate each movie record with a specific user. For example, if one Sales user creates a movie, we'll store that user's username. When another user logs in, we'll be able to distinguish their movies from the first user's movies.

## Step 2 — Retrieve the authenticated username and assign ownership

Now that our Movie entity can store a username, we need to know which user is currently logged in.

We don't want the user to type their username manually when creating a movie. Instead, we'll retrieve the authenticated username from Jakarta Security.

### 2B — Assign the username when creating a movie

In the same file, find `addMovie()`.

> “When someone creates a movie, our service asks Jakarta Security who is logged in.
>
> We take that username and assign it to the movie before saving it.
>
> So if `sales01` creates a movie, that movie is automatically associated with `sales01`. The user doesn't need to enter their username.”


```
public void addMovie(Movie movie) {
    LocalDateTime now = LocalDateTime.now();

    movie.setCreateTime(now);
    movie.setUpdateTime(now);



    String username =
        securityContext.getCallerPrincipal().getName();

    movie.setUsername(username);



    movieRepository.insert(movie);
}
```

### Code explanation

| Code                            | What it does                                  |
| ------------------------------- | --------------------------------------------- |
| `LocalDateTime.now()`           | Gets the current date and time                |
| `setCreateTime(now)`            | Records when the movie was created            |
| `setUpdateTime(now)`            | Records the latest update time                |
| `getCallerPrincipal()`          | Retrieves the current authenticated principal |
| `getName()`                     | Gets the username                             |
| `movie.setUsername(username)`   | Assigns the current user as the movie owner   |
| `movieRepository.insert(movie)` | Saves the movie to the database               |

## Step 4 — Restrict movie listings using authentication and roles


Now we need to apply our application rules.

First, users must be authenticated. Second, they must have a supported role. Finally, we'll decide which records to return.

Sales users should see their own movies, while Administration users should see all movies.

Where: Return to:

`src/main/java/dmit2015/service/MovieService.java`

Find `getAllMovies()`.



```
public List<Movie> getAllMovies() {

    String username =
        securityContext.getCallerPrincipal().getName();

    if (username.equalsIgnoreCase("anonymous")) {
        throw new RuntimeException(
            "Access Denied. Anonymous users do not have " +
            "permission to access this method."
        );
    }

    boolean hasRequiredRoles =
        securityContext.isCallerInRole("Sales")
        || securityContext.isCallerInRole("Administration");

    if (!hasRequiredRoles) {
        throw new RuntimeException(
            "Access denied. You role does not have " +
            "permission to access this method."
        );
    }

    boolean hasSalesRole =
        securityContext.isCallerInRole("Sales");

    if (hasSalesRole) {
        return movieRepository.findAllByUsername(username);
    }

    return movieRepository.findAll();
}
```

### 4A — Check whether the user is authenticated


> “Before returning movie data, we check whether the caller is authenticated. We don't want an anonymous user accessing this service method.”

```
String username =
    securityContext.getCallerPrincipal().getName();

if (username.equalsIgnoreCase("anonymous")) {
    throw new RuntimeException(
        "Access Denied. Anonymous users do not have " +
        "permission to access this method."
    );
}
```





### 4B — Check whether the user has an allowed role

> “Being logged in doesn't automatically mean you can access everything.
>
> We also need to check the user's role. In our application, only Sales and Administration are supported for this operation.”

```
boolean hasRequiredRoles =
    securityContext.isCallerInRole("Sales")
    || securityContext.isCallerInRole("Administration");

if (!hasRequiredRoles) {
    throw new RuntimeException(
        "Access denied. You role does not have " +
        "permission to access this method."
    );
}
```

Explanation:

- `isCallerInRole("Sales")` checks for the Sales role.
- `isCallerInRole("Administration")` checks for the Administration role.
- `||` means OR.
- If neither role is present, the method denies access.




### 4C — Return different records depending on the role

> “This is where our application becomes multi-user.
>
> For Sales users, we filter movies by their username.
>
> For Administration users, we return all movies.
>
> Notice that we're using the same service method, but the result depends on the authenticated user's role.”

```
boolean hasSalesRole =
    securityContext.isCallerInRole("Sales");

if (hasSalesRole) {
    return movieRepository.findAllByUsername(username);
}

return movieRepository.findAll();
```

Explanation:

- If the user has the Sales role, retrieve only movies matching their username.
- Otherwise, after passing the earlier role check, return all movies.

## Step 5 — Handle security exceptions in JSF managed beans


In Step 4, we added security checks to `MovieService.java`. When a user does not have permission to access an operation, the service can throw a `RuntimeException`.

Now we need to make sure our JSF managed beans handle these exceptions and display meaningful messages instead of leaving the user with an unhandled error.



> “We've added security rules in our service layer. But what happens if a user tries to perform an operation and the service denies access?
>
> Our service can throw an exception. We need to catch that exception in our JSF managed bean and display a warning message to the user.
>
> We'll review this exception handling in our Create, Edit, Delete, and List views.”

### Step 5A — MovieCreateView\.java

Where to go in IntelliJ IDEA

Open:

`src/main/java/dmit2015/view/MovieCreateView.java`

Find the method `onCreateNew()`.


```
public String onCreateNew() {
    String nextPage = "";
    try {
        movieService.addMovie(newMovie);
        Messages.addFlashGlobalInfo(
            "Create was successful. {0}", newMovie.getId()
        );
        nextPage = "index?faces-redirect=true";
    } catch (RuntimeException ex) {
        Messages.addGlobalWarn(ex.getMessage());
    } catch (Exception e) {
        Messages.addGlobalError(
            "Create was not successful. {0}", e.getMessage()
        );
    }
    return nextPage;
}
```

### Code explanation

| Code                                      | What it means                                                                    |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| `String nextPage = "";`                   | Initializes the navigation result to stay on the current page                    |
| `try`                                     | Starts the block where we attempt to create the movie                            |
| `movieService.addMovie(newMovie)`         | Calls the service to save the new movie                                          |
| `Messages.addFlashGlobalInfo(...)`        | Stores a success message that survives the redirect                              |
| `nextPage = "index?faces-redirect=true"`  | Redirects to the movie list after successful creation                            |
| `catch (RuntimeException ex)`             | Handles runtime exceptions, including application-level access-denied exceptions |
| `Messages.addGlobalWarn(ex.getMessage())` | Displays the exception message as a warning                                      |
| `catch (Exception e)`                     | Handles other exceptions                                                         |
| `Messages.addGlobalError(...)`            | Displays an error message when creation fails                                    |
| `return nextPage`                         | Returns the navigation outcome                                                   |




> “If the service throws a runtime exception, our Create View catches it here.
>
> We use `Messages.addGlobalWarn()` to display the exception message as a warning.
>
> If movie creation succeeds, we display a success message and redirect to the movie list.
>
> If an exception occurs, we don't set the redirect, so the user remains on the Create page and can see the message.”
