# Part 4 – Preventing Over-Posting with DTOs and MapStruct


## Introduction — What are we doing in Part 4?

> “In the previous lessons, we created a REST API using our `TodoItem` entity, tested it using IntelliJ's HTTP Client, and explored Swagger UI.
>
> But there's a problem with returning our entity directly.
>
> The entity contains properties such as creation time and update time that we might not want to expose to clients.
>
> In this lesson, we'll create a Data Transfer Object, or DTO, to control which properties clients can send and receive.
>
> We'll also use MapStruct to convert between the entity and DTO automatically.
>
> Finally, we'll create a new REST resource that works with DTOs instead of exposing our persistence entity directly.”

## What we'll build

At the end of this part, we'll have two REST resources:

| Resource              | URL                                          | Returns                   |
| --------------------- | -------------------------------------------- | ------------------------- |
| `TodoItemResource`    | `http://localhost:8090/restapi/todos-entity` | `TodoItem` entity objects |
| `TodoItemDtoResource` | `http://localhost:8090/restapi/todos`        | `TodoItemDto` objects     |

Both resources use the same `TodoItemRepository` and database records. We are not creating a second database table.

## Step 1 — Understand why we need a DTO



### What we're doing

Our existing API returns all properties of the `TodoItem` entity.

Our entity contains:

```java
private Long id;
private String task;
private boolean done;
private Integer version;
private LocalDateTime createTime;
private LocalDateTime updateTime;
```

But a client application doesn't necessarily need to see or submit every property.

A Data Transfer Object (DTO) gives us control over the data exposed by the REST API.

### Entity versus DTO

| Entity property | DTO property | Explanation                            |
| --------------- | ------------ | -------------------------------------- |
| `id`            | `id`         | Identifies the to-do item.             |
| `task`          | `name`       | Renamed to a client-friendly property. |
| `done`          | `complete`   | Renamed to a client-friendly property. |
| `version`       | `version`    | Retained for version tracking.         |
| `createTime`    | Not included | Internal timestamp is hidden.          |
| `updateTime`    | Not included | Internal timestamp is hidden.          |



> “Our entity represents how we store data in the database.
>
> A DTO represents the data that we want to exchange with clients.
>
> They don't have to contain exactly the same properties.
>
> For example, we can rename `task` to `name` and `done` to `complete`.
>
> We can also leave out internal properties such as creation and update timestamps.
>
> This helps prevent over-posting, where a client submits values for properties that it shouldn't be allowed to control.”

## Step 2 — Create the TodoItemDto class



### What we're doing

We'll create a Java class containing only the properties we want clients to use.

### Where to go in IntelliJ IDEA

**Open the following file:**

`dmit2015-todo-restapi/src/main/java`

Right-click `java` → New → Package.

Create:

`dmit2015.dto`

Right-click the package → New → Java Class.

Name it:

`TodoItemDto`

The resulting path is:

`dmit2015-todo-restapi/src/main/java/dmit2015/dto/TodoItemDto.java`

### Add the code

```java
package dmit2015.dto;

import jakarta.validation.constraints.NotBlank;
import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

import java.io.Serializable;

@Data
@NoArgsConstructor
@AllArgsConstructor
public class TodoItemDto implements Serializable {

    private Long id;

    @NotBlank(message = "Name value cannot be blank.")
    private String name;

    private boolean complete;

    private Integer version;

}
```

### Code explanation

| Code                      | Explanation                                                   |
| ------------------------- | ------------------------------------------------------------- |
| `@Data`                   | Lombok generates getters, setters, and other utility methods. |
| `@NoArgsConstructor`      | Generates a constructor with no parameters.                   |
| `@AllArgsConstructor`     | Generates a constructor accepting all fields.                 |
| `implements Serializable` | Allows the object to be serialized.                           |
| `id`                      | Identifies the record.                                        |
| `@NotBlank`               | Ensures the name is not blank.                                |
| `name`                    | Client-facing equivalent of entity property `task`.           |
| `complete`                | Client-facing equivalent of entity property `done`.           |
| `version`                 | Keeps the version property available for updates.             |

### Example DTO JSON

```json
{
  "id": 1,
  "name": "Create JAX-RS demo project",
  "complete": true,
  "version": 0
}
```

Notice that the DTO does not include `createTime` or `updateTime`.

> “We're creating a class named `TodoItemDto`.
>
> It contains only four properties: ID, name, complete, and version.
>
> We're also adding a NotBlank validation annotation to the name property.
>
> We don't need to include the creation and update timestamps because those are internal details.
>
> This DTO is what we'll return to the client instead of returning the entire entity.”

## Step 3 — Create the TodoItemMapper interface



### What we're doing

Our entity and DTO use different property names.

The entity uses `task` and `done`, while the DTO uses `name` and `complete`.

We need a way to convert between them.

We will uses MapStruct, which generates mapping code during compilation.

### Where to go in IntelliJ IDEA

Under:

`dmit2015-todo-restapi/src/main/java`

Create the package:

`dmit2015.mapper`

We will use the IntelliJ file template DMIT2015 JAX-RS DTO Mapper. Entity: TodoItem

Create:

`dmit2015/mapper/TodoItemMapper.java`

### updated code

```java
package dmit2015.mapper;

import dmit2015.dto.TodoItemDto;
import dmit2015.entity.TodoItem;
import org.mapstruct.Mapper;
import org.mapstruct.Mapping;
import org.mapstruct.Mappings;
import org.mapstruct.ReportingPolicy;
import org.mapstruct.factory.Mappers;

@Mapper(unmappedTargetPolicy = ReportingPolicy.IGNORE)
public interface TodoItemMapper {

    TodoItemMapper INSTANCE = Mappers.getMapper(TodoItemMapper.class);

    @Mappings({
            @Mapping(target = "name", source = "task"),
            @Mapping(target = "complete", source = "done"),
    })
    TodoItemDto toDto(TodoItem entity);

    @Mappings({
            @Mapping(target = "task", source = "name"),
            @Mapping(target = "done", source = "complete"),
    })
    TodoItem toEntity(TodoItemDto dto);

}
```

### Code explanation

| Code                                             | Explanation                                        |
| ------------------------------------------------ | -------------------------------------------------- |
| `@Mapper`                                        | Marks this interface as a MapStruct mapper.        |
| `ReportingPolicy.IGNORE`                         | Ignores warnings for unmapped target properties.   |
| `Mappers.getMapper(...)`                         | Retrieves the generated mapper implementation.     |
| `toDto(...)`                                     | Converts a `TodoItem` entity into a `TodoItemDto`. |
| `toEntity(...)`                                  | Converts a DTO into a `TodoItem` entity.           |
| `@Mapping(target = "name", source = "task")`     | Copies entity `task` into DTO `name`.              |
| `@Mapping(target = "complete", source = "done")` | Copies entity `done` into DTO `complete`.          |

### How the mapping works


MapStruct converts between the two classes, including task ↔ name and done ↔ complete.


## Step 4 — Change the existing entity resource path


### What we're doing

We already have `TodoItemResource.java` from Part 2.

That resource currently uses:

```text
@Path("todos")
```

Our new DTO resource will also use `/restapi/todos`.

Two resource classes should not expose the same HTTP methods at the same path, so the we changes the original entity resource to a different URL.

### Where to go in IntelliJ IDEA

**Open the following file:**

`dmit2015-todo-restapi/src/main/java/dmit2015/resource/TodoItemResource.java`

### Find

```text
@Path("todos")
```

### Replace with

```text
@Path("todos-entity")
```

Do not replace the whole class. Only change the `@Path` annotation.

### After this change

| Resource            | URL                                          |
| ------------------- | -------------------------------------------- |
| Original entity API | `http://localhost:8090/restapi/todos-entity` |
| New DTO API         | `http://localhost:8090/restapi/todos`        |

> “We want the DTO version of the API to use `/restapi/todos`.
>
> But our original entity resource already uses that path.
>
> So we'll change the original resource path to `todos-entity`.
>
> That allows both resources to exist in the same application while using different URLs.”

## Step 6 — Implement GET all using DTOs

### What we're doing

The GET all endpoint will retrieve the entities from the repository and convert each one into a DTO before returning the result.

### Where to add the code

Inside `TodoItemDtoResource.java`, below the injected repository.

### code

```java
@GET
public Response findAllTodoItemsTodoItems() {
    return Response.ok(
            todoItemRepository
                    .findAll()
                    .stream()
                    .map(TodoItemMapper.INSTANCE::toDto)
                    .collect(Collectors.toList())
    ).build();
}
```

### Code explanation

| Code                                   | Explanation                         |
| -------------------------------------- | ----------------------------------- |
| `findAll()`                            | Retrieves all `TodoItem` entities.  |
| `.stream()`                            | Creates a stream of the results.    |
| `.map(TodoItemMapper.INSTANCE::toDto)` | Converts each entity to a DTO.      |
| `.collect(Collectors.toList())`        | Collects the DTOs into a list.      |
| `Response.ok(...)`                     | Returns the DTO list with HTTP 200. |



> “Notice that we're still calling `findAll()` on the repository.
>
> But before returning the results, we're mapping each entity into a DTO.
>
> That means the client receives `name` and `complete` instead of `task` and `done`.
>
> The creation and update timestamps are also excluded.”

## Step 8 — Implement POST using a DTO

### What we're doing

Now we'll allow clients to create a new to-do item using the DTO property names.

Instead of submitting `task` and `done`, clients submit `name` and `complete`.

###  code

```java
@POST
public Response createTodoItemTodoItem(TodoItemDto dto, @Context UriInfo uriInfo) {
    TodoItem newTodoItem = TodoItemMapper.INSTANCE.toEntity(dto);

    String errorMessage = JavaBeanValidator.validateBean(newTodoItem);
    if (errorMessage != null) {
        return Response
                .status(Response.Status.BAD_REQUEST)
                .entity(errorMessage)
                .build();
    }

    try {
        todoItemRepository.add(newTodoItem);
    } catch (Exception ex) {
        return Response
                .serverError()
                .entity(ex.getMessage())
                .build();
    }

    URI location = UriBuilder
            .fromPath(uriInfo.getPath())
            .path("{id}")
            .build(newTodoItem.getId());

    return Response
            .created(location)
            .build();
}
```

### Code explanation

| Code                          | Explanation                                 |
| ----------------------------- | ------------------------------------------- |
| `TodoItemDto dto`             | Receives JSON in DTO format.                |
| `toEntity(dto)`               | Converts the DTO into a `TodoItem` entity.  |
| `validateBean(newTodoItem)`   | Checks validation on the mapped entity.     |
| `todoItemRepository.add(...)` | Saves the entity.                           |
| `UriBuilder`                  | Builds a location for the created resource. |
| `Response.created(location)`  | Returns HTTP 201 Created.                   |

> “When the client sends JSON, Jakarta REST converts it into a DTO.
>
> Then we use MapStruct to convert that DTO into a `TodoItem` entity.
>
> After validating the entity, we save it through the repository.
>
> If the operation succeeds, we return 201 Created.”

## Step 9 — Implement PUT using a DTO

### What we're doing

The PUT endpoint receives a DTO, converts it into an entity, validates the updated values, and updates the existing database record.

###  code

```java
@PUT
@Path("{id}")
public Response updateTodoItemTodoItem(@PathParam("id") Long id, TodoItemDto dto) {
    if (!id.equals(dto.getId())) {
        throw new BadRequestException();
    }

    TodoItem existingTodoItem = todoItemRepository
            .findById(id)
            .orElseThrow(NotFoundException::new);

    TodoItem updatedTodoItem = TodoItemMapper.INSTANCE.toEntity(dto);

    String errorMessage = JavaBeanValidator.validateBean(updatedTodoItem);
    if (errorMessage != null) {
        return Response
                .status(Response.Status.BAD_REQUEST)
                .entity(errorMessage)
                .build();
    }

    existingTodoItem.setVersion(updatedTodoItem.getVersion());
    existingTodoItem.setTask(updatedTodoItem.getTask()); //added
    existingTodoItem.setDone(updatedTodoItem.isDone()); //added

    try {
        todoItemRepository.update(existingTodoItem);
    } catch (OptimisticLockException ex) {
        return Response
                .status(Response.Status.CONFLICT) //added
                .entity("The data you are trying to update has changed since your last read request.")
                .build();
    } catch (Exception ex) {
        return Response
                .serverError()
                .entity(ex.getMessage())
                .build();
    }

    TodoItemDto updatedDto = TodoItemMapper.INSTANCE.toDto(existingTodoItem);
    return Response.ok(updatedDto).build();
}
```

### Code explanation

| Code                            | Explanation                                  |
| ------------------------------- | -------------------------------------------- |
| `@PUT`                          | Handles HTTP PUT requests.                   |
| `@Path("{id}")`                 | Identifies the record to update.             |
| `id.equals(dto.getId())`        | Ensures the URL and DTO IDs match.           |
| `toEntity(dto)`                 | Converts the DTO into an entity.             |
| `validateBean(updatedTodoItem)` | Checks the mapped entity's validation rules. |
| `setVersion(...)`               | Copies the supplied version.                 |
| `setTask(...)`                  | Copies the updated task.                     |
| `setDone(...)`                  | Copies the updated completion status.        |
| `OptimisticLockException`       | Handles an optimistic locking conflict.      |
| `toDto(existingTodoItem)`       | Converts the updated entity back into a DTO. |
| `Response.ok(updatedDto)`       | Returns the DTO with HTTP 200.               |



> “Our PUT endpoint now receives a DTO instead of an entity.
>
> We verify that the ID in the URL matches the ID in the request body.
>
> Then we convert the DTO to an entity, validate it, and copy the editable properties to the existing record.
>
> After updating the repository, we convert the result back into a DTO before returning it to the client.
>
> That means both our request and response use the DTO format.”

## Step 10 — Implement DELETE

### What we're doing

The DELETE endpoint remains very similar to the entity-based version because it only needs the record's ID.


```java
@DELETE
@Path("{id}")
public Response deleteTodoItemTodoItem(@PathParam("id") Long id) {

    TodoItem existingTodoItem = todoItemRepository
            .findById(id)
            .orElseThrow(NotFoundException::new);

    try {
        todoItemRepository.delete(existingTodoItem);
    } catch (Exception ex) {
        return Response
                .serverError()
                .encoding(ex.getMessage())
                .build();
    }

    return Response.noContent().build();
}
```

### Code explanation

| Code                       | Explanation                                |
| -------------------------- | ------------------------------------------ |
| `@DELETE`                  | Handles DELETE requests.                   |
| `@Path("{id}")`            | Receives the ID of the record to delete.   |
| `findById(id)`             | Retrieves the existing entity.             |
| `NotFoundException`        | Returns 404 when no record exists.         |
| `delete(existingTodoItem)` | Deletes the entity through the repository. |
| `Response.noContent()`     | Returns HTTP 204 on success.               |

### Test request

```http
DELETE http://localhost:8090/restapi/todos/2
```

Expected: `204 No Content` if the record exists and is deleted successfully.

> “For DELETE, we don't need to map an entity to a DTO.
>
> The client only provides the ID of the record to remove.
>
> We find that record using the repository, delete it, and return 204 No Content.”
