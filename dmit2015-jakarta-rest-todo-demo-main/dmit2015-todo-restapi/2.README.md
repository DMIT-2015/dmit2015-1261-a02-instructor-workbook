# Part 2 – Building the To-Do REST API with Jakarta RESTful Web Services


## Introduction — What are we doing in Part 2?

> “In Part 1, we examined our To-Do entity, repository, Jakarta REST configuration, and WildFly server.
>
> Now we're going to create REST API endpoints that allow another application to manage our to-do items.
>
> We'll use HTTP GET to retrieve records, POST to create a record, PUT to update a record, and DELETE to remove a record.
>
> We'll also validate incoming data and return the appropriate HTTP status codes.
>
> Finally, we'll use IntelliJ's HTTP Client to test our API before building a frontend.”

### What we'll build

| HTTP method | Endpoint              | Purpose                  | Successful response |
| ----------- | --------------------- | ------------------------ | ------------------- |
| GET         | `/restapi/todos`      | Retrieve all to-do items | `200 OK`            |
| GET         | `/restapi/todos/{id}` | Retrieve one to-do item  | `200 OK`            |
| POST        | `/restapi/todos`      | Create a to-do item      | `201 Created`       |
| PUT         | `/restapi/todos/{id}` | Update a to-do item      | `200 OK`            |
| DELETE      | `/restapi/todos/{id}` | Delete a to-do item      | `204 No Content`    |



## Step 1 — Rename HelloApplication to JaxRsApplication



### What we're doing

The starter project contains a Jakarta REST application class named `JaxRsApplication`.

we renames it to `JaxRsApplication` and changes the base application path to `/restapi`.

### Where to go in IntelliJ IDEA

1. Open `dmit2015-todo-restapi/src/main/java/dmit2015/dmit2015todorestapi/HelloApplication.java`.
2. Right-click `JaxRsApplication` → **Refactor** → **Rename** → enter `JaxRsApplication`.
3. Change the application path.

### Replace or edit the exisiting code with following code

```java
package dmit2015.dmit2015todorestapi;

import jakarta.ws.rs.ApplicationPath;
import jakarta.ws.rs.core.Application;

@ApplicationPath("/restapi")
public class JaxRsApplication extends Application {

}
```

### Code explanation

| Code                           | Explanation                                         |
| ------------------------------ | --------------------------------------------------- |
| `@ApplicationPath("/restapi")` | Establishes the base path for REST API requests.    |
| `extends Application`          | Identifies this as a Jakarta REST application.      |
| `JaxRsApplication`             | The more descriptive name chosen by us. |

> “The class name isn't important for how REST works, but we'll rename it to make its purpose clearer.
>
> The important change is the application path.
>
> We're changing it to `/restapi`, so our REST resources will use that as their base path.”

## Step 2 — Create the JavaBeanValidator helper class



### What we're doing

When a client sends invalid information, we want to return a meaningful validation message instead of saving invalid data.

Our `TodoItem` entity already has the constraint:

```java

```

we use a reusable `JavaBeanValidator` helper class to check these validation constraints.

### Where to go in IntelliJ IDEA

1. Go to `dmit2015-todo-restapi/src/main/java`.
2. Create the package `common.validation`.
3. Use the IntelliJ file template **DMIT2015 JavaBean Validator**.
4. Generate `common/validation/JavaBeanValidator.java`.


> “We're creating a helper method that checks the validation annotations on an object.
>
> If there are validation errors, it returns a JSON object describing which properties failed.
>
> If there are no errors, it returns null.
>
> We'll use this method when creating and updating to-do items.”



### Code explanation

| Code                                          | Explanation                                                    |
| --------------------------------------------- | -------------------------------------------------------------- |
| `validateBean(T typeInstance)`                | Checks the supplied object against its validation annotations. |
| `Validation.buildDefaultValidatorFactory()`   | Creates a Jakarta Bean Validation factory.                     |
| `.validate(typeInstance)`                     | Finds any validation violations.                               |
| `Json.createObjectBuilder()`                  | Builds a JSON object containing error messages.                |
| `return jsonObjectBuilder.build().toString()` | Returns validation errors as a JSON string.                    |
| `return null`                                 | Means no validation violations were found.                     |



## Step 3 — Create the TodoItemResource class

```java
package dmit2015.resource;

import common.validation.JavaBeanValidator;
import dmit2015.entity.TodoItem;
import dmit2015.repository.TodoItemRepository;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

import jakarta.ws.rs.core.UriInfo;

import java.net.URI;

@ApplicationScoped
@Path("todos")
@Consumes(MediaType.APPLICATION_JSON)
@Produces(MediaType.APPLICATION_JSON)
public class TodoItemResource {

    @Inject
    private TodoItemRepository todoItemRepository;

    // REST API methods will go here.
}
```


### Code explanation

| Code                                    | Explanation                                                  |
| --------------------------------------- | ------------------------------------------------------------ |
| `@ApplicationScoped`                    | Makes this a CDI-managed bean.                               |
| `@Path("todos")`                        | Defines the resource path.                                   |
| `@Consumes(MediaType.APPLICATION_JSON)` | Specifies JSON input.                                        |
| `@Produces(MediaType.APPLICATION_JSON)` | Specifies JSON output.                                       |
| `@Inject`                               | Injects the existing repository.                             |
| `TodoItemRepository`                    | Provides the database operations used by the REST endpoints. |

## Step 6 — Implement POST to create a new to-do item


### What we're doing

Now we'll create an endpoint that accepts a JSON object and saves it as a new `TodoItem`.

we validate the object before adding it to the database.

### Existing code


```java
@POST
public Response createTodoItemTodoItem(TodoItem newTodoItem, @Context UriInfo uriInfo) {

    String errorMessage = JavaBeanValidator.validateBean(newTodoItem);
    if (errorMessage != null) {
        return Response
                .status(Response.Status.BAD_REQUEST)
                .entity(errorMessage)
                .build();
    }

    try {
        todoItemRepository.add(newTodoItem);
    } catch (Exception ex) {
        return Response
                .serverError()
                .entity(ex.getMessage())
                .build();
    }

    URI location = uriInfo.getAbsolutePathBuilder()
            .path(String.valueOf(newTodoItem.getId()))
            .build();

    return Response
            .created(location)
            .build();
}
```

### Code explanation

| Code                                  | Explanation                                             |
| ------------------------------------- | ------------------------------------------------------- |
| `@POST`                               | Handles HTTP POST requests.                             |
| `TodoItem newTodoItem`                | Receives the JSON request body as a Java object.        |
| `JavaBeanValidator.validateBean(...)` | Checks the object's validation rules.                   |
| `Response.Status.BAD_REQUEST`         | Returns 400 if validation fails.                        |
| `todoItemRepository.add(...)`         | Saves the new item.                                     |
| `@Context UriInfo`                    | Gives access to information about the request URL.      |
| `getAbsolutePathBuilder()`            | Starts building the URL for the newly created resource. |
| `Response.created(location)`          | Returns 201 Created with a Location header.             |

### Example HTTP request

```http
POST http://localhost:8090/restapi/todos
Content-Type: application/json

{
  "task": "Test REST API endpoints",
  "done": false
}
```

### Expected result

`201 Created`

The response includes a `Location` header pointing to the newly created item, such as `/restapi/todos/4` if its generated ID is 4.

> “When creating a to-do item, we don't need to pass an ID because the database generates it.
>
> We also don't need to supply the creation time or version.
>
> First, we validate the incoming data. If the task is blank, we return 400 Bad Request.
>
> Otherwise, we add the item to the repository and return 201 Created.
>
> We also include the Location header so the client knows where to find the new resource.”

## Step 7 — Implement PUT to update a to-do item



### What we're doing

The PUT endpoint updates an existing item.

There are several important checks:

- The ID in the URL must match the ID in the JSON body.
- The incoming data must pass validation.
- The record must exist.
- A stale version can cause an optimistic locking conflict.

### Update code


```java
@PUT
@Path("{id}")
public Response updateTodoItemTodoItem(@PathParam("id") Long id, TodoItem updatedTodoItem) {
    if (!id.equals(updatedTodoItem.getId())) {
        throw new BadRequestException();
    }

    String errorMessage = JavaBeanValidator.validateBean(updatedTodoItem);
    if (errorMessage != null) {
        return Response
                .status(Response.Status.BAD_REQUEST)
                .entity(errorMessage)
                .build();
    }

    TodoItem existingTodoItem = todoItemRepository
            .findById(id)
            .orElseThrow(NotFoundException::new);

    existingTodoItem.setVersion(updatedTodoItem.getVersion());
    existingTodoItem.setTask(updatedTodoItem.getTask()); //added
    existingTodoItem.setDone(updatedTodoItem.isDone()); //added

    try {
        todoItemRepository.update(existingTodoItem);
    } catch (OptimisticLockException ex) {
        return Response
                .status(Response.Status.CONFLICT) //added
                .entity("The data you are trying to update has changed since your last read request.")
                .build();
    } catch (Exception ex) {
        return Response
                .serverError()
                .entity(ex.getMessage())
                .build();
    }

    return Response.ok(existingTodoItem).build();
}
```


### Code explanation

| Code                                 | Explanation                                          |
| ------------------------------------ | ---------------------------------------------------- |
| `@PUT`                               | Handles HTTP PUT requests.                           |
| `@Path("{id}")`                      | Identifies the item being updated.                   |
| `id.equals(updatedTodoItem.getId())` | Checks that the URL ID and JSON ID match.            |
| `validateBean(...)`                  | Rejects invalid task values.                         |
| `findById(id)`                       | Retrieves the existing record.                       |
| `setVersion(...)`                    | Copies the submitted version for optimistic locking. |
| `setTask(...)`, `setDone(...)`       | Copies the editable properties.                      |
| `OptimisticLockException`            | Handles a version conflict.                          |
| `Response.Status.CONFLICT`           | Returns HTTP 409 Conflict.                           |
| `Response.ok(...)`                   | Returns HTTP 200 on success.                         |

### Example HTTP request

```http
PUT http://localhost:8090/restapi/todos/4
Content-Type: application/json

{
  "id": 4,
  "task": "Finish testing REST API",
  "done": true
}
```


> “When updating a resource, the ID in the URL must match the ID in the request body.
>
> If they don't match, we return 400 Bad Request.
>
> We also validate the updated data and make sure the record exists.
>
> Then we copy the editable properties to the existing entity and update it using the repository.
>
> If there's an optimistic locking conflict, we return 409 Conflict instead of 400 Bad Request.”

## Step 8 — Implement DELETE to remove a to-do item


### What we're doing

Finally, we'll create an endpoint that deletes a to-do item using its ID.

### Existing code


```java
@DELETE
@Path("{id}")
public Response deleteTodoItem(@PathParam("id") Long id) {

    TodoItem existingTodoItem = todoItemRepository
            .findById(id)
            .orElseThrow(NotFoundException::new);

    try {
        todoItemRepository.delete(existingTodoItem);
    } catch (Exception ex) {
        return Response
                .serverError()
                .encoding(ex.getMessage())
                .build();
    }

    return Response.noContent().build();
}
```

### Code explanation

| Code                             | Explanation                         |
| -------------------------------- | ----------------------------------- |
| `@DELETE`                        | Handles HTTP DELETE requests.       |
| `@Path("{id}")`                  | Identifies the item to delete.      |
| `findById(id)`                   | Checks whether the item exists.     |
| `NotFoundException`              | Returns 404 if the item is missing. |
| `todoItemRepository.delete(...)` | Removes the entity.                 |
| `Response.noContent()`           | Returns 204 No Content on success.  |

### Example

```http
DELETE http://localhost:8090/restapi/todos/2
```

### Expected result

`204 No Content`

> “For DELETE, the client passes the ID of the resource to remove.
>
> We first check whether that record exists.
>
> If it doesn't exist, we return 404 Not Found.
>
> Otherwise, we delete it and return 204 No Content.
>
> A 204 response tells the client the operation succeeded, but there is no response body.”
